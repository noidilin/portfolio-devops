GCP auth from your AWS SSO model

Goal: before we migrate labs/05-static-site-ec2/ to GCE, you should be able to answer one safety question: “Which identity is this terminal about to use, and what can it do?”

Your existing anchor: in AWS Lab 05, local Terraform uses an IAM Identity Center agent permission set; Terraform-created EC2/GitHub/workload roles are constrained with boundaries and scoped PassRole. In GCP, the best-practice shape is usually human login → service account impersonation → attached service account on GCE, not long-lived keys.

That last column is not just a translation. It reflects Google’s documented preference for attached service accounts, service account impersonation, and federation over service account keys.1

2. The core GCP IAM sentence

GCP IAM is still “who can do what on which resource,” but the nouns differ:

Grant a principal a role on a resource using an allow policy.
  • Principal: user, group, service account, workforce identity, workload identity.
  • Role: collection of permissions; you grant roles, not individual permissions.
  • Resource: project, folder, organization, VM, bucket, service account, etc.
  • Allow policy: bindings from roles to principals, attached to resources and inherited down the hierarchy.2
AWS habit to retire: don’t look first for “the role I assumed.” For human CLI use, ask: active gcloud account? active project? am I impersonating a service account? does ADC differ from gcloud?

3. The terminal has two credential stores

This is the first practical trap. gcloud credentials and Application Default Credentials are separate. Google’s docs call this out explicitly.3

QuestionCommandWhy you care
Who will gcloud use?gcloud auth listLike checking which AWS SSO account/profile is active.
Which project is default?gcloud config list projectMany commands infer project from config.
Which token does CLI have?gcloud auth print-access-tokenDebug raw REST calls and expiry.
What will Terraform/client libraries use?gcloud auth application-default print-access-tokenADC may be a different identity from gcloud.

gcloud config set compute/region asia-east1

gcloud auth list
gcloud config list account project compute/region

# For Terraform/client libraries if not impersonating yet:
gcloud auth application-default login

# Later, preferred for apply identity:
gcloud auth application-default login \
  --impersonate-service-account=tf-apply@PROJECT_ID.iam.gserviceaccount.com

4. Best-practice first design for the GCE migration

  1. Human principal: your user gets enough access to inspect the project and impersonate a narrowly-scoped Terraform service account.
  2. Terraform service account: can create/manage the lab’s GCE VM, firewall, Artifact Registry repo, and runtime service account. This is your GCP counterpart to the AWS local operator / GitHub apply role boundary pattern.
  3. Runtime service account: attached to the GCE VM. It gets only pull/read/logging permissions needed at boot. This replaces the EC2 instance profile.
  4. No JSON keys: use impersonation locally and Workload Identity Federation in GitHub. Treat service account keys like leaked long-lived AWS access keys waiting to happen.
