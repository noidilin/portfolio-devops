Map GCP login lanes to your AWS roles

Lesson 3 goal: repair the fuzzy part from Lesson 2 by mapping each GCP auth lane to your real AWS lab shapes: local aws-sso, GitHub OIDC provider, and GitHub Actions plan / image push / apply roles.

Tangible win: after this lesson, you should be able to look at a command or workflow step and say: “this belongs to the gcloud, ADC, or metadata lane — and the GCP identity should be this user or service account.”

1. The three GCP lanes are caller lanes

Do not start with “which login command did I run?” Start with who is calling the Google API?

2. Local terminal: your aws-sso maps to two GCP stores

In AWS, your third-party aws-sso tool makes an IAM Identity Center session usable by AWS profiles. In GCP, split that habit:

# Manual gcloud commands — gcloud lane

gcloud auth login
gcloud config set project PROJECT_ID
gcloud auth list
gcloud config list account project

# Terraform / local app code — ADC lane

gcloud auth application-default login \
  --impersonate-service-account=tf-plan@PROJECT_ID.iam.gserviceaccount.com

Google recommends service account impersonation when you need a service account in development: you start from an authenticated user, then request short-lived credentials for the service account; this avoids persistent service account keys.1

Safe local pattern for this lab: your human account should be allowed to impersonate a small Terraform service account. That is the closest GCP match to “I enter locally through a controlled AWS deploy role,” but the command lives in the ADC lane when Terraform is the caller.

3. GitHub OIDC provider: not a lane, an entrance gate

Your AWS bootstrap has an account-level OIDC provider for token.actions.githubusercontent.com, then each role trust policy checks aud and sub:

  • *-github-plan: PRs and main.
  • *-github-image-push: main only.
  • *-github-apply: protected GitHub environment.

In GCP, the equivalent entrance is a Workload Identity Pool Provider. It trusts GitHub OIDC, maps claims such as assertion.sub, assertion.repository, and assertion.repository_owner, then uses an attribute condition to reject unwanted tokens before they can impersonate anything.2, 4

# Conceptual GCP equivalent of the AWS OIDC provider + trust filters
issuer: https://token.actions.githubusercontent.com/
attribute mapping:
  google.subject = assertion.sub
  attribute.repository = assertion.repository
  attribute.repository_owner = assertion.repository_owner
attribute condition:
  assertion.repository_owner == "YOUR_ORG"
  # tighten later: repository, ref, or environment

4. GitHub plan / push / apply: use CI ADC via WIF

Once GitHub is admitted by Workload Identity Federation, GitHub Actions usually creates a short-lived credential file. Future steps — Terraform, gcloud, Docker auth helpers — consume it through environment variables such as GOOGLE_APPLICATION_CREDENTIALS. That makes CI mostly an ADC lane story.2, 4

Important difference: AWS “role to assume” becomes, in this GCP design, a service account to impersonate. The permission bundle is not attached as an inline policy to the service account. Instead, the service account is granted IAM roles on projects/resources.

5. GCE runtime: metadata lane replaces EC2 instance profile

Your EC2 lab likely creates an instance profile so the VM can access AWS APIs without static keys. The GCP equivalent is: create a user-managed service account, grant it only runtime roles, and attach it to the VM. Google recommends user-managed service accounts for VMs, not relying on broad default service accounts.3

gcloud compute instances create VM_NAME \
  --service-account=vm-runtime@PROJECT_ID.iam.gserviceaccount.com \
  --scopes=cloud-platform

The cloud-platform scope is not the permission grant by itself; IAM roles on the service account still bound what the VM can do.
