gcloud auth login vs ADC

Goal: understand the GCP auth vocabulary from Lesson 1 well enough to choose the right login command before running gcloud, Terraform, Docker/Artifact Registry auth, or code.

One-sentence answer: gcloud auth login gives credentials to the gcloud CLI; gcloud auth application-default login writes Application Default Credentials for libraries and tools that use Google’s ADC lookup strategy. They are separate stores.

1. The AWS mental model trap

With your AWS setup, aws-sso login makes a profile usable, and many tools follow the AWS credential chain from that profile/session. GCP splits this more visibly:

CLI lane

gcloud auth login stores credentials that gcloud commands use by default. It also sets the active account in the active gcloud configuration.

Application lane

gcloud auth application-default login stores credentials in the ADC well-known location. Client libraries and many tools use this lane.

Google’s docs state both sides explicitly: the gcloud CLI itself does not use ADC to access Google Cloud resources, and application-default login has no effect on accounts set up by gcloud auth login.1, 2

2. What is gcloud auth login?

Use this when you are typing gcloud commands: create a VM, list Artifact Registry repos, configure Docker auth, inspect IAM policies, enable APIs.

gcloud auth login

gcloud auth list
gcloud config set project PROJECT_ID
gcloud compute instances list

It creates/stores credentials in the gcloud configuration directory and makes one principal active for CLI commands. You can have multiple credentialed accounts, but only one active account in a configuration unless you override it.

Session-safety habit: before destructive commands, check both identity and project: gcloud auth list and gcloud config list account project.

3. What is ADC?

Application Default Credentials is not one credential type. It is a search strategy: Google auth libraries look in known places and pick credentials automatically. The documented order is:

  1. GOOGLE_APPLICATION_CREDENTIALS environment variable
  2. Local ADC file from gcloud auth application-default login
  3. Attached service account from metadata server when running on GCP, such as GCE

For local development, application-default login writes an ADC file such as ~/.config/gcloud/application_default_credentials.json on macOS/Linux.3

gcloud auth application-default login

gcloud auth application-default print-access-token

# Inspect whether the local ADC file exists
ls -l ~/.config/gcloud/application_default_credentials.json

5. The three identities you may have at once

In one terminal, these can all differ:

# 1. Active gcloud account

gcloud auth list

# 2. Active gcloud project/config

gcloud config list account project auth/impersonate_service_account

# 3. ADC identity used by libraries/tools

gcloud auth application-default print-access-token

That third command prints a token, not a friendly identity. In practice, if confused, revoke and recreate ADC intentionally, or use impersonation so the intended service account is explicit.

6. Recommended pattern for your GCE migration lab

  1. Human exploration: gcloud auth login. Use this for learning and manual inspection.
  2. Local Terraform: ADC with service account impersonation. This mirrors your AWS idea of “local operator enters through a controlled deploy identity,” but without static keys.
  3. Runtime VM: no login command. Attach a user-managed service account to GCE; metadata server provides short-lived tokens.
  4. CI/CD: Workload Identity Federation from GitHub, not service account keys.
Avoid: “I downloaded a service account JSON key so Terraform works.” That is the GCP equivalent of creating a long-lived deploy access key. Use it only when federation/impersonation cannot work.
